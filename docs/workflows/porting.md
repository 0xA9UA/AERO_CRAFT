# Java ↔ Bedrock porting

Start with `aero inspect SOURCE --output inventory.json`, then `aero port SOURCE --to bedrock --output assessment` (or `--to fabric`, `neoforge`, `forge`). Source can be a JAR, MCADDON/MCPACK/ZIP or a source directory. The plan records source hashes and creates an unassessed feature ledger. This is an assessment, not an automatic behavior converter.

1. **Establish the source.** Keep the original immutable. Record version, loader, artifact SHA-256, dependency versions and licenses. Inspect nested `.mcpack` manifests; inspect dependency JARs separately. Use `inspect --members` to record individual member hashes. Prefer source when available. For binaries, use `decompile --engine vineflower`, corroborate with CFR and the selected JDK's `javap -p -c -s`. REA complements this with package inventories, JavaScript analysis, evidence exports and optional native providers. Never assume REA's native provider can recover an arbitrary JVM mod by itself.
2. **Write a feature matrix.** Split registries, recipes, inventories, energy/fluids, redstone, entities, networking, UI, saves, world generation and rendering. Each feature needs a source member/method, target implementation, tests, and a status: unassessed, implemented, adapted, verified, or unsupported. Item registration counts measure content coverage, not working mechanics.
3. **Create a target.** Use a pinned profile and keep engine APIs behind adapters. Pure state transitions should accept plain state and return explicit updates, costs, outputs and failures. Characterize source quirks instead of silently “fixing” them during a fidelity port.
4. **Translate data deliberately.** `recipe` translates simple shaped/shapeless crafting in either direction. It requires explicit mappings for custom IDs and rejects tags, alternatives, conditions, NBT/components, special stations and custom serializers. The Java output schema targets 1.21.1. Revisit data formats for another Minecraft version. Cooking time/XP, machine recipes and reusable tools need custom implementations. Keep original texture and sound licenses; model inheritance and UV orientation need separate checks.
5. **Adapt mechanics.** Java capabilities, tile/block entities, mixins, native packets and custom renderers do not map directly to Bedrock scripts. Conversely Bedrock components, events and forms need Java registrations, state and networking. Map coordinates, directions, tick schedules, unloaded chunks, dimensions, item identity, durability and interaction gestures explicitly. Bound per-tick work.
6. **Persist safely.** Preserve Bedrock behavior-pack header UUIDs. Introduce versioned schemas, migration tests and a recovery policy for interrupted inventory operations. A sequence of world dynamic-property writes is not an atomic database transaction. Preserve item metadata when moving or cloning stacks. Test full inventories, failed native mutations, ownership and restart recovery.
7. **Validate in layers.** Pure tests → API typecheck → static structure → deterministic package → actual dedicated server → actual process restart → connected desktop/touch/controller clients. Record what was observed at each layer. Headless servers do not establish rendered textures, audio or physical player UI correctness.
8. **Release evidence.** Record source and output hashes, build/tool versions, tests, runtime logs and unresolved differences. Keep original third-party binaries, decompiled sources, runtime worlds and credentials out of public releases unless their redistribution is authorized.

The IC2 work that motivated this suite showed why model parent resolution, charging UI state, transaction recovery and native save tests must be separate acceptance criteria. Its original proprietary inputs and private transcripts are not included in this repository.
